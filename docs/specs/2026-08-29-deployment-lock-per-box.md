# deployment lock per box

> Every box's deployment is a committed lock: the compose files, overrides and Dockerfiles it actually runs are versioned in the repo under deployments/<box>/, secrets stay in the never-committed .env, lobes init --from-lock restores a box from it, and lobes doctor reports `lock_drift` when the deployed files no longer match.

## Audience

- the fleet operator running lobes on more than one box (today: DGX Spark, Jetson AGX Thor, Jetson AGX Orin), a third party who wants to adopt a working variation without owning the box it was measured on, and two machine consumers — lobes doctor, which diffs the lock against what is deployed, and CI, which gates what may be committed.

## Before → After

- Before: the deployed ~/.lobes/docker-compose.yml is the real serving contract and nothing tracks its divergence from the packaged template. Found during #199 t11 prep on 2026-08-25: the Spark's compose was hand-edited with the DSpark --speculative-config baked into the vllm-primary command while the Thor's happened to equal the template — a difference only a live diff revealed.
- After: every box's deployment is reproducible from the repo: lobes init --from-lock materialises a committed variation verbatim, a third party can adopt one they have never run, lobes doctor names any divergence as `lock_drift`, and no credential or peer origin has ever entered git.

## Why it matters

- three costs follow from that gap: a deployment cannot be shared or restored without re-applying every hand edit from memory; re-scaffolding is unsafe on any hand-edited box, so operators avoid lobes init --apply and the passthrough drift the `gateway_passthrough` check guards against accumulates; and evidence transcripts cite only `MODEL_GEAR_VERSION` plus a shape name, which under-describes what actually ran.

## Requirements

- the genuinely GENERATED per-(card,shape) artifacts a lock must capture are docker-compose.shape.yml (`_compose`.`SHAPE_OVERLAY`, written by init when a shape drops a core role) and the docker-compose.gpu.yml / docker-compose.gpu-audio.yml pair (init.py `render_gpu_overrides`, written when the card declares `gpu_access`=runtime and REMOVED when it does not). `_sync_gpu_overrides` force-writes and deletes these on every --apply.
  - honesty: a lock captured on a csv-mode card restores both GPU overlays, and one captured on a devices card restores neither — the remove-on-mismatch behaviour of `_sync_gpu_overrides` survives a lock round-trip
- no CI job scans for committed secrets today: .github/workflows/ holds only tests.yml (test / lint / site-build / version-check) and publish.yml, and neither runs gitleaks, trufflehog or detect-secrets. 'Secrets stay in .env' is currently enforced only by the .gitignore pattern and reviewer attention, so a committed-lock practice that widens what gets committed needs a mechanical gate to keep the claim honest.
  - honesty: a PR adding a credential-shaped value to any committed file fails a REQUIRED CI job, not an advisory one
- lobes doctor already has the exact shape a `lock_drift` finding needs: `_check`(id, passed, severity, message, remediation) builds every finding, `_diagnose` assembles them, and `_scaffold_files_check` is a direct precedent (it compares expected scaffold dests against what is on disk). doctor --fix already has the write lane and its convention — write absent files and keys, never rewrite an existing .env line — which a lock restore must obey.
  - honesty: `lock_drift` names the specific differing files, and doctor --fix still never rewrites an existing .env line
- --from-lock is a distinct SOURCE, not a fourth input to the renderer: it materialises the committed files verbatim and does NOT re-resolve profile+shape. init's other three axes (topology --single/--fleet/--audio, card --profile, shape --shape) all feed lobes/profiles/render.py; --from-lock bypasses that path entirely, which is what makes a restore byte-identical to what the box runs today.
  - honesty: restoring a lock on a box whose DETECTED card differs from the lock's still produces the lock's files verbatim — profile/shape resolution is provably not consulted
- the repo publishes ALL docker variations under deployments/, not only the boxes this operator happens to run — a chooser's catalog, so a third party can pick a variation and adopt it. This widens the practice beyond the issue's stated backup/restore motive.
  - honesty: a variation this operator does not run is present in the repo and materialisable by --from-lock on a machine that has never served it
- each variation folder carries a SEPARATE spec/info file, in the same folder, naming what the variation is and the measured result of running it. Provenance: measured results live in docs/evidence/ (57 committed transcripts) today, so the info file must CITE its evidence transcript rather than restate the numbers, or the two drift.
  - honesty: every variation info file either names an existing docs/evidence/ transcript path or states no measured result; a test asserts the cited path exists
- variation identity is MACHINE TYPE OR SETUP — spark and jetson clear, other machines possibly different, and for an AI accelerator the accelerator itself. This reuses vocabulary lobes already has: lobes/runtime/`_detect.py` resolves a card from nvidia-smi name+`compute_cap`, /proc/meminfo, the Jetson device-tree model and hostname, and lobes/profiles/builtin/ is already keyed base/orin/spark/thor. Identity is NOT the hostname, though `_detect` does probe one.
  - honesty: two different physical machines of the same type resolve to the SAME variation id, and no variation id contains a hostname
- nothing is ever retyped by hand: the secret half of a deployment is materialised by files or code, not operator memory. Two mechanisms already exist in-tree and generalise. (1) scripts/gen-api-key.py GENERATES a bearer key with the stdlib secrets module, writes it into the gitignored deployment .env and deliberately never prints it — a secret that is created, not typed. (2) cf-tunnel.env.example is committed verbatim and the owner copies it to the gitignored .cf-tunnel.env — a committed shape whose values are filled locally.
  - honesty: a fresh box reaches a serving state without the operator typing any secret value by hand: every credential is generated by code or read from a gitignored file
- the split lands as a .\*.env FAMILY read alongside .env, which compose already supports natively: every service in lobes/templates/fleet/docker-compose.yml uses the long-form '`env_file`: \[{path: .env, required: false}\]', and that list takes further entries. Adding a second required:false entry per service is a backwards-compatible template change — an absent file changes nothing.
  - honesty: adding the second `env_file` entry leaves a deployment that has no such file behaving byte-identically — compose starts and serves exactly as before
- adopting '\*.env' ignored requires an explicit un-ignore for the goldens: 37 tracked files match it today, all under tests/goldens (5 at the root — base/orin/spark/thor/template-defaults — and 32 under shapes/). They are already tracked so they would not vanish, but tests/goldens/README.md states a future built-in profile's golden 'must still be generated and committed' — that new file would be silently unstageable. A '!tests/goldens/\*\*/\*.env' negation (or renaming the goldens) is mandatory, not optional.
  - honesty: after the gitignore change a newly generated golden for a new built-in profile is stageable, proven by a check rather than remembered
- the committed lock is RENAMED out of the .env family entirely — proposed 'deployment.lock.toml', matching the house format (lobes/profiles/builtin/\*.toml and `builtin_shapes`/\*.toml are already TOML). Rationale: the .env. prefix rule makes anything in that family committable BY CONSTRUCTION, so an env-shaped committed file is the one place a copied real .env would land undetected. A name that is visibly not an env file removes the invitation. Note 'lock.env' is disqualified automatically — the .env SUFFIX rule ignores it.
  - honesty: the committed lock filename matches NEITHER the .env suffix rule nor the .env. prefix rule, asserted by a test on the name itself
- c9's CI secret gate becomes load-bearing rather than optional once anything deployment-shaped is committed: the positional gitignore rule protects files NAMED like env files, and the lock is deliberately named otherwise, so the naming rule provides it zero protection. A scanner is the only mechanical guard left on the lock itself.
  - honesty: the secret scanner covers the lock path specifically, not merely the repository default set
- c25's allowlist protects ONLY the .env-derived lock — it does not extend to the files the practice commits VERBATIM. #214 explicitly lists docker-compose.override.yml among them, and `_compose`.`LOCAL_OVERRIDE` is the one file lobes never writes, never templates and cannot vouch for: an operator may inline anything in it, including an environment: block with a real token. The Spark's baked --speculative-config proves operators do hand-edit these files. Every verbatim-committed file needs the same scanning gate as the lock, or the secret-free claim covers only the half that was never at risk.
  - honesty: the secret scanner runs over every committed variation file — the four compose files and the Dockerfiles — not only the generated lock; proven by a test that plants a token in a committed override and sees CI fail
- a committed variation can become UNBUILDABLE with time: Dockerfile.gateway installs lobes-cli==${`MODEL_GEAR_VERSION`} from PyPI, or a .devN wheel from TestPyPI for a PR build (lines 12-28). A variation captured at a dev version references an artifact that may not outlive the PR, so c14's promise that a third party can materialise a variation they never ran fails at BUILD time, not at restore time. The capacity-pool frame recorded this same class as deviation d2.
  - honesty: a variation whose gateway version is no longer installable is DETECTED as unbuildable with a clear message, rather than failing deep inside a docker build
- the frame gates against a leak but specifies no RECOVERY from one. Blast radius is larger than one box: under proxy-lobes each <PREFIX>`_PEER_API_KEY` is a COPY of the peer's own inbound `GATEWAY_API_KEY`, so rotating one leaked key requires updating every peer holding that copy. scripts/gen-api-key.py --force rotates locally only. A committed secret also survives git rm — it needs history rewrite. A documented rotation-and-revocation path belongs in the spec, since it changes what ships, not merely how it is built.
  - honesty: the rotation path is written down and names every place a copy of the key lives, and a leaked-key drill can be followed end to end by someone who did not write it
- --from-lock must refuse, or loudly warn on, a MACHINE-TYPE MISMATCH between the lock and the restoring box. Because c13 makes --from-lock bypass profile/shape resolution entirely, it also bypasses `_sync_gpu_overrides` — so restoring a variation captured on a devices-mode card onto a csv-mode board (or the reverse) silently produces a deployment whose GPU access is wrong, the exact failure the generated overlays exist to prevent. Nothing in the frame today makes the lock's declared identity checked against detection.
  - honesty: restoring a lock whose declared machine type differs from what `_detect` resolves does NOT silently proceed — it refuses by default, and any override is explicit

## Honesty conditions

- a box restored with --from-lock produces a byte-identical compose/override/Dockerfile set to what it ran before, proven by diff, and its .env is left untouched
- --from-lock against a box with a live .env leaves every existing .env line byte-identical, asserted by a test rather than by convention
- the lock's rendered keys are derived from `profile_env` itself, or a test diffs them against the matching tests/goldens file — the two cannot disagree silently
- a secret-shaped value committed into a lock is caught by a machine gate, not by a reviewer noticing
- uv build produces a wheel containing no deployments/ path, asserted by a test rather than by inspection
- no committed lock contains a \*`_PEER_ORIGIN` value, checked mechanically rather than by reading
- a variation with no acceptance transcript renders as an explicit 'no measured result' in its info file and in any listing — never as a blank a reader could mistake for a measurement
- git check-ignore proves .env, .cf-tunnel.env and .secrets.env are ignored while .env.example and .env.sample are not
- feeding the lock writer a .env that contains `GATEWAY_API_KEY` produces a lock without it — the allowlist is proven by construction, not by redaction
- each named audience can actually reach the artifact: the operator via lobes init --from-lock, the third party from a repo checkout alone with no access to the measured box, doctor via a file diff, and CI via a required job — no audience is served only by prose
- the after-state is checkable as a whole, not claim by claim: a box restored from its committed variation serves the same model at the same knobs as before the restore, and git log over the repo shows no commit ever introduced a credential or peer origin
- the before-state is evidenced, not remembered: the 2026-08-25 Spark/Thor compose divergence is recorded in a citable transcript or issue #214 itself, so the motivating incident survives as more than a claim in this frame
- each of the three costs is separately observable today — a hand-edited box that cannot be re-scaffolded safely, a transcript citing only version plus shape, and at least one accumulated passthrough drift the `gateway_passthrough` check would flag
- all three success signals are mechanical and run without a human judging them: each is a test, a doctor check, or a CI job, and each FAILS on a deliberately broken input, not merely passes on a good one

## Success signals

- three checks, all mechanical: (1) a box restored with lobes init --from-lock produces a byte-identical compose/override/Dockerfile set to what it ran before, with its .env untouched; (2) lobes doctor reports `lock_drift` naming the differing files when they diverge, and passes when they do not; (3) a CI job fails a PR that commits a credential- or origin-shaped value anywhere, including in a lock.

## Scope / boundaries

- the merge-only .env guarantee must not be weakened: `_compose`.`MERGE_ONLY_FILES` is exactly {`ENV_FILE`} and its docstring names `GATEWAY_API_KEY`, every \*`_PEER_`\*, `COMPOSE_PROFILES` and `HF_TOKEN` as the operator-typed state no template can regenerate. Every other scaffold file is overwrite-on---force. A --from-lock restore inherits that split: it may replace compose/Dockerfiles wholesale, never .env.
- the lock must not become a second, drifting copy of tests/goldens/: goldens are the (profile, shape, template) render contract and their README already states that editing one machine's bundle must leave the others byte-identical. A deployments/<box>/ lock that re-states rendered knobs would need its own regeneration story or it silently disagrees with the goldens it duplicates.
- today's leak guard is weak and the practice must not rest on it: .gitignore line 151 is the bare pattern .env, applied at any depth, so deployments/<box>/.env is unstageable by accident — but ANY other name (the issue's env.lock.example included) is committable, leaving redaction as unenforced discipline. Superseded in mechanism by c22's positional rule, which is what makes the guard structural rather than a habit.
- a top-level deployments/ directory is automatically excluded from the wheel: pyproject.toml's \[tool.hatch.build.targets.wheel\] declares packages = \["lobes"\], so committed per-box locks never ship to PyPI consumers. The lock is a repo artifact, not a distributed one.
- peer origins are internal information and are blanked in the committed env lock, alongside `GATEWAY_API_KEY`, every \*`_PEER_API_KEY`(S) and `HF_TOKEN`. This frame does NOT retro-scrub the 57 committed evidence transcripts that already carry tailnet origins in cleartext — that is a separate correction to the evidence convention, filed, not folded in here.
- a variation's info file must state UNVALIDATED honestly rather than imply a result it does not have: CLAUDE.md's #108 rule makes most shipped shapes declared-not-measured (all four Orin shapes and thor-muse have no acceptance transcript), so 'choose a variation and see the result' will show 'no measured result' for most of the catalog on day one. Publishing the catalog must not manufacture the appearance of evidence.
- the gitignore convention is a POSITIONAL naming rule, not a per-file line: a '.env' SUFFIX is ignored (covering .env itself, .cf-tunnel.env, .secrets.env and every future secret dotfile by construction), a '.env.' PREFIX is allowed (.env.example, .env.sample, .env.lock). This replaces .gitignore's current bare '.env' — which matches only that exact component and is why line 155 must spell out .cf-tunnel.env separately — and makes a forgotten ignore line structurally impossible. Naming consequence: the committed redacted artifact is named .env.lock (allowed by the prefix rule, deliberately), not the issue's proposed env.lock.example, which matches neither rule and would be committable only by accident of suffix ordering.
- the lock's contents are an ALLOWLIST of rendered keys, never a denylist-redacted copy of the deployed .env. Evidence: `profile_env` renders only <ROLE>`_`{MODEL,`SERVED_NAME`,`GPU_MEM_UTIL`,`MAX_MODEL_LEN`,QUANTIZATION,`KV_CACHE_DTYPE`} plus attention-backend and max-num-seqs knobs — non-secret by construction — and 36 of the 37 committed goldens contain no `API_KEY`/`HF_TOKEN`/`PEER_ORIGIN` at all. The single hit, tests/goldens/template-defaults.env, lists those key NAMES with empty values because it is the template's ${VAR} default surface, not a render. A denylist over a real .env silently ships the next secret key someone adds; an allowlist cannot.

## Non-goals

- the lock must not displace the scaffold-based deployment model: CLAUDE.md states lobes is scaffold-based, not checkout-based, and that there is deliberately no compose file at the repo root. deployments/<box>/ adds committed deployment artifacts beside that model — --from-lock is an opt-in restore path, never the default lobes init source.

## Assumptions

- compose files and Dockerfiles are copied VERBATIM from the wheel, never value-rendered: lobes/runtime/`_compose.py`'s `SINGLE_TEMPLATES`/`FLEET_TEMPLATES`/`AUDIO_TEMPLATES` map template name to dest name and `write_scaffold` copies bytes. Only .env is rendered from the profile+shape. So 'rendered compose' in the issue is accurate for .env and the two GENERATED overlay families only; for the compose files themselves the lock captures (packaged template version + operator hand edits).
- docker-compose.override.yml already exists as the supported home for per-box hand edits: `_compose`.`LOCAL_OVERRIDE` is never scaffolded or written by lobes, is docker compose's own convention, and is explicitly named in the -f chain so it stays honoured when an audio or shape overlay suppresses auto-discovery. The Spark's baked --speculative-config could live there and would already survive lobes init --apply --force, which reframes the issue's motivating incident as partly a documentation gap rather than a missing mechanism.
- the repo ALREADY commits byte-for-byte rendered .env artifacts: tests/goldens/ holds base.env, orin.env, spark.env, thor.env and 40+ shapes/<shape>`__`<card>.env, regenerated deterministically by tests/goldens/regen.py and diffed by `test_profile_goldens.py` / `test_shape_goldens.py`. The issue's env.lock.example overlaps this almost entirely, so the honest delta a per-box lock adds is the NON-deterministic part — hand edits and operator-typed keys — not the rendered part.
- the per-box divergence the lock captures is real and current: the Spark works with the DSpark drafter and the Thor does not, so two boxes both hosting cortex need genuinely different rendered state. The lock ROUTES AROUND #204's missing per-box override rather than fixing it — #204 stays open.
- the lock is invalidated by a FIRST-CLASS VERB, not only by hand edits: lobes switch writes model keys straight into .env via `_env`.`set_env` (switch.py:510,546), which is exactly the key family the allowlist lock captures. So a normal, documented, dry-run-guarded operation silently makes the committed lock stale — the frame's drift story assumes hand edits are the source of divergence, and they are not the only one.

## Open parks

- [unknown_nonblocking] nothing forces a lock to be re-committed after a hand edit, so a stale lock claims to describe a box it no longer describes — arguably worse than no lock; whether doctor's `lock_drift` finding is enough of a forcing function, or the practice needs a boot-time or CI-time gate, is undecided
- [unknown_nonblocking] doctor's `lock_drift` can only compare the LOCAL variation against this box's deployed files — a catalog of variations for boxes nobody here runs has nothing to diff against, so most committed variations are unverifiable by the same mechanism that keeps the local one honest
- [unknown_nonblocking] whether the committed catalog should hold variations at all for machine types nobody in this mesh runs — c14 promises adoption by a third party, but c34 shows a variation can outlive its buildable wheel and c36 shows a cross-type restore is hazardous, so the catalog's value may be documentary rather than executable
- [unknown_nonblocking] residual surprise risk this pass could not close: no lens examined what a MALICIOUS or careless contributor's committed variation could do to someone who adopts it — a variation is executable configuration (build contexts, mounted paths, image refs) and adopting one from the repo is closer to running a script than reading a doc

## Resolved vagueness

- [unknown_blocking] a full-fidelity .env restore is blocked on #204: .env records no distinction between lobes-managed keys and operator-typed ones, so a lock cannot tell which redacted keys a restore should re-render from the profile and which the operator must retype — resolved: descoped by mechanism, not by fixing #204: the lock never needs to know which redacted keys are lobes-managed vs operator-typed, because no key is retyped either way. Rendered knobs come back from the committed lock; secrets come back generated (gen-api-key.py's model) or from a gitignored .\*.env the operator holds once per box. #204's managed-key manifest stays open but stops blocking a full-fidelity restore.
