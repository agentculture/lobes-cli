# innereye: lobes hosts ComfyUI

> lobes hosts ComfyUI as a managed tenant: one command warms the image backend after a reboot, its peak cost is DECLARED against the same card the gears draw from so a known-bad pairing is refused, and a peer on another machine reaches it through the gateway's bearer — while ComfyUI itself publishes no host port and is reachable only on the compose network
> instruction: The announcement is only true once an acceptance transcript lands under docs/evidence/; until then every surface must say DECLARED/UNVALIDATED per #108

## Audience

- The lobes operator running a card that hosts image generation, and innereye as the only client today — plus any mesh peer that wants to render without being told an origin out of band
  - instruction: Check the exported spec names both the operator and innereye, and that GET /capabilities is the discovery path a peer uses rather than a hand-typed origin

## Before → After

- Before: ComfyUI is a hand-started foreground venv process with no supervision, no restart policy, no structured logging and no lifecycle manager of any kind — no systemd unit, no cron, nothing in shell history. It sits entirely outside lobes' accounting, and it is currently DOWN
  - instruction: Confirm against the box: systemctl --user list-units | grep -i comfy is empty, crontab -l says no crontab, ps shows no process, and start-comfy.sh is a bare exec with no daemonization
- After: One lobes command warms the image backend after a reboot and 'lobes capabilities' says whether it is warm; ComfyUI runs as a compose service that publishes no host port, reachable only as <http://comfyui:8188> on the compose network, with its 65G model tree bind-mounted read-only from the host; the gateway fronts it at /v1/render behind the same bearer the fleet already enforces; and innereye renders against it once it has been taught the facade wire
  - instruction: Verify on the Spark: reboot or stop the service, run the single up verb, then 'lobes capabilities' shows innereye ready, and 'innereye render --endpoint <gateway>' completes a FLUX job end to end

## Why it matters

- Two GPU tenants share one unified-memory card. The fleet is carefully budgeted; the renderer is started by hand and is invisible to that budget, so neither side can assume the card. The operator wants one place to manage the load, and lobes is already that place
  - instruction: The spec must not overclaim: lobes gains a place to DECLARE the renderer's cost and refuse a known-bad pairing, not an engine that meters memory

## Scope / boundaries

- ComfyUI keeps binding 127.0.0.1 and lobes terminates auth in front of it: the gateway's `do_POST` runs `_authorized`() unconditionally before route dispatch (lobes/gateway/server.py `do_POST`), so any new POST family inherits the bearer for free, but `do_GET` only gates paths under /v1/ (server.py:4426) — so the render family must be spelled /v1/... or it ships unauthenticated
  - instruction: Spell the render family under /v1/ so `do_GET`'s existing bearer check at server.py:4426 covers it; prove the 401 with a negative control rather than assuming the prefix
- lobes does not, and will not here, compute a memory budget: nothing in render.py, schema.py, shapes.py or `shape_render.py` ever sums `gpu_mem_util` across roles or compares it to the card's total. Budgets are declared env text the operator is solely responsible for. The one multi-role guard, `overcommitted_groups` (`shape_render.py`:305-335), is a boolean co-residency veto driven by an operator-authored `exclusive_roles` list whose arithmetic is a prose reason string — so 'budgeted co-residency' for ComfyUI means a DECLARATION plus a veto, not an accounting engine
  - instruction: Do not add budget arithmetic. The declared peak's only consumer is the `exclusive_roles` veto; say so in the doc so no reader infers metering
- The mesh gives discovery for free but NOT reach: Announcement/RoleInfo/Fingerprint verification (`_mesh_wire.py`:64-146, `_mesh_routing.py`:214-259) would advertise an innereye lane fine, but the only forward primitive is `open_upstream` (server.py:581-621), whose method is hardcoded POST, single-hop, and single-response. ComfyUI's submit-then-poll-then-GET-binary shape has no home in it — mirroring how /v1/realtime needed its own bespoke bridge rather than reusing the POST forwarder
  - instruction: Decide explicitly whether the innereye lane is announced to the mesh at all in v1, or announced private — noting that no operator-facing producer sets private today (server.py:4981-4994 never emits the key)
- innereye holds NO filesystem coupling to the ComfyUI host, by explicit design: 'Nothing touches the local filesystem. Artifacts come back over /view and the model list over the API, never by reading ComfyUI's output/ or models/ directories. That is what lets the same adapter drive a server on another host' (comfyui.py:24-27). So lobes may containerize ComfyUI and move its model directory freely — but lobes inherits the disk growth innereye states it will never clean: ComfyUI keeps its own counter-named copy of every artifact under output/ (`SERVER_SIDE_COPY_NOTE`, comfyui.py:70-73)
  - instruction: lobes owns the output/ growth innereye will never clean — either a retention policy on the bind-mounted output dir or an explicit statement that the operator owns it
- Two different exposures, deliberately not the same: INSIDE the compose network the comfyui service offers ComfyUI's whole native API and its whole output tree; OUTWARD through the gateway only the job-scoped /v1/render facade is published (c38). The bind-mounted output directory is how the operator reaches artifacts, including ComfyUI's own duplicate copies — lobes owns no retention policy for them
  - instruction: State both exposures side by side in the reference doc so no reader concludes the native surface is reachable from off-box
- V1 SCOPE: innereye and the heavy generate lanes are declared MUTUALLY EXCLUSIVE on one card via the existing \[\[`exclusive_roles`\]\] mechanism (schema.py:219-250), so v1 never attempts co-residency. This is why the unmeasured comfy-aimdo behaviour does not block first support: every bad outcome in that risk is conditional on sharing the card.   - instruction: Declare the group with roles=\["cortex","innereye"\], a shapes= list naming the resolving shape, and a reason quoting the measured bare-venv numbers. ## Assumptions

- The repo's own decision rule for a new role (docs/colleague-stack.md:331-357, echoed at lobes/roles.py:95-98) is that a role is justified only when a catalog change, a profile/shape change, or a responsibilities token cannot express the need. ComfyUI is none of those three — it is not a checkpoint, budget or behaviour variant of any existing lane — so the rule is arguably satisfied, but the box demands an eleventh clear the same bar hand and associate did, explicitly
- There is exactly one non-container supervision precedent in lobes: lobes/runtime/`_tunnel.py`, which Popens cloudflared with `start_new_session`, writes .cloudflared.pid, and stops it by SIGTERM/SIGKILL against the recorded pid — explicitly 'NOT a compose service'. Everything else (every role in `ROLE_SERVICE`, up.py:81-92) is a compose service, and `_health.py` shells out to docker inspect. Operator decision c19 takes the compose path, so the tunnel pattern is NOT generalized — and per c13 the containerization does not face a custom GB10 torch build, only the stock cu130 wheel index
- CORRECTION to the issue's endpoint list: innereye does not drive the endpoints the issue names. It prefers ComfyUI 0.33.2's /api/jobs surface (GET /api/jobs, GET /api/jobs/{id}, POST /api/jobs/{id}/cancel) and falls back to GET /history/{id} + GET /queue only for older servers (innereye/backends/comfyui.py:264-305, 361-379). It never opens a websocket at all — its own spec records that a stdlib-only client cannot easily consume /ws, so --wait polls. So the WS tunnel the gateway would otherwise owe is NOT required by the only client
- CORRECTION to the issue's 'on a GB10 the torch build is the fiddly part': install-code.sh records 'pip3 install torch torchvision --index-url <https://download.pytorch.org/whl/cu130>' — the stock upstream PyTorch cu130 wheel index, not a custom GB10 rebuild; +cu130 is PyTorch's ordinary CUDA-13.0 local tag. Combined with ZERO third-party custom nodes (`custom_nodes` holds only ComfyUI's own `websocket_image_save.py` and an inert .example), the install is far more reproducible than the issue implies
- The server is NVIDIA's DynamicVRAM/aimdo build, not stock memory management: startup logs 'comfy-aimdo integrated Linux GPU RAM headroom: 7788 MB', 'DynamicVRAM support detected and enabled', 'Using async weight offloading with 2 streams', 'Enabled pinned memory 112149.0', against 'Total VRAM 124611 MB, total RAM 124611 MB' on the GB10. So the tenant already has a headroom-aware allocator (comfy-aimdo 0.4.13) that no fleet gear has — that headroom number, not a `gpu_mem_util` fraction, may be the honest budget lever
- Because the facade is not ComfyUI's native wire, innereye must change client code — not just --endpoint — to render through the gateway. That is a coordination obligation on agentculture/innereye, whose issue #268 assumed a config-only change on its side
  - instruction: File this back on innereye as a follow-up issue before the lane is advertised, so the only client is not surprised by its own ask
- The deployment lock reaches this lane automatically and mostly correctly: the new Dockerfile and compose service are verbatim-committed files the required secrets-scan CI job covers, and the render knobs enter the \[env\] allowlist because it is DERIVED from render.py's own tables rather than a redacted .env. But the model-path knob may be caught by the '`_URL`'-suffix exclusion or miss it depending on its name, and the 65G tree itself is host state no lock can restore
- Concurrency is handled by ComfyUI itself, not by lobes: it serializes submissions through its own queue, so two agents rendering at once produce queue depth rather than two concurrent ~32 GB peaks. That is the assumption the declared peak (c17) rests on, and nothing in the frame states it — if it is wrong, the co-residency veto is calibrated against the wrong number

## Hard questions

- The architecture fork the issue asks lobes to decide: is ComfyUI an ELEVENTH first-class role (innereye) in ROLES, or a new NON-ROLE tenant class that lobes budgets, supervises and reverse-proxies without pretending it is a model gear? The repo's own test (colleague-stack.md:331-357) says reach for a role only when a catalog change, a profile/shape change, or a responsibilities token cannot express it — and none of the three can. But the stt/tts precedent shows a non-vLLM sidecar CAN be a role, at the cost of a facade path per endpoint
- What IS the budget declaration for a tenant with no `gpu_mem_util`? Candidates: (a) a declared peak-GiB figure that participates only in the `exclusive_roles` co-residency veto; (b) ComfyUI's own --reserve-vram N, which reserves memory FOR others rather than capping the tenant; (c) comfy-aimdo's headroom setting, already live at 7788 MB on this box. None is a fraction, and the schema has no non-fractional knob
- Does 'start-on-demand' ship at all in v1? It requires a lifecycle actuator in the gateway's request path, which today never imports `_compose` — a separation that currently holds absolutely. The cheaper v1 is: lobes owns start/stop/status only, and a request to a cold backend gets an honest 503/warming rather than triggering a boot
- `ROLE_PATH` is one string per role, but the render lane is several endpoints over two methods. Does innereye advertise a single facade path that the gateway fans out behind, or does `ROLE_PATH` itself widen to a tuple — which would touch every existing role's row? (resolved: OPERATOR DECISION: innereye advertises a SINGLE facade path, /v1/render, and the gateway fans out behind it to ComfyUI's submit/poll/fetch endpoints — exactly as /v1/audio/\* fans out to the realtime bridge today. `ROLE_PATH` stays one string per role and no other role's row is touched. The named cost is accepted: innereye needs a client change to speak the facade rather than raw ComfyUI, so this is NOT a config-only change on innereye's side)

## Resolved vagueness

- [unknown_blocking] Whether the tenant stays a bare venv (generalizing `_tunnel.py`'s pidfile pattern, the only non-container supervision in lobes) or gets containerized (fitting all existing compose machinery, at the cost of reproducing the cu130 torch stack and bind-mounting 65G of weights). Both are viable; the choice drives most of the implementation — resolved: Containerized as a compose service, with the model directory bind-mounted from the host so it stays reachable outside Docker. The bare-venv / `_tunnel.py`-pidfile option is rejected: compose is what makes it maintainable.
- [unknown_nonblocking] Whether lobes serves innereye's /api/jobs surface or the older /history+/queue fallback, and what happens to the artifact-duplication innereye states it will never clean (ComfyUI keeps a counter-named copy of every output under output/) — resolved: OPERATOR DECISION: expose it all under the ComfyUI docker service. The container carries ComfyUI's FULL native surface on the compose network (both the 0.33.2 /api/jobs family and the older /history + /queue fallback — lobes picks neither, it hosts the server and both are reachable internally), and every artifact, including the duplicate counter-named copies ComfyUI keeps for itself, lives under the single bind-mounted output directory. That mount is the exposure: the operator sees and manages the artifacts directly from the host, so lobes ships no retention or cleanup policy. This is INTERNAL exposure only — what the gateway publishes outward stays job-scoped per c38
- [unknown_blocking] Whether comfy-aimdo's DynamicVRAM, its GPU-RAM-headroom figure, and its ~112 GiB pinned-memory allocation behave the same inside the container as on the bare venv — and whether that pinned memory is safe co-resident with the vLLM gears on a 121 GB unified-memory card — resolved: OPERATOR-ACCEPTED (path 2): settled by a GATING SPIKE rather than by design. The aimdo-in-container question — headroom figure, DynamicVRAM detection, and the ~112 GiB pinned-memory line, each compared against the bare-venv baseline — is carried plan-side as a BLOCKING plan risk and becomes task t1, so nothing downstream merges until it reports.
