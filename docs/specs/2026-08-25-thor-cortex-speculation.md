## Scope / boundaries

- the 1M YaRN window and DSpark cannot both survive on the Thor. The Spark refused the DSpark boot at `max_model_len`=1048576 / util 0.58 ('needs 51.47 GiB KV; available 40.76'), and the Thor is strictly worse per GiB of KV: it runs `kv_cache_dtype`=auto (the validated #109 divergence) where the Spark runs fp8, and its 1M pool is 1,114,504 tokens vs the Spark's 1,271,476 at the same util. So any Thor speculation arm inherits the same forced trade-down to the checkpoint's native 262144 — a served-contract change visible through lobes capabilities, not a private dial
  - instruction: Record the KV pool size and concurrency multiple vLLM reports for each arm, so the served-contract cost of the drafter is measured on this box rather than inherited from the Spark's numbers.
- PR #202 has ALREADY changed what the Thor would render, and nobody measured it on `sm_110`. The d1 transcript records the Thor deployment as 'lobes init --shape spark-lobe --apply --force on the thor card', so the Thor borrows spark-lobe — the very shape 830bbf3 moved to DSpark @ 262144. A routine re-render on the Thor today would arm DSpark argv on a box where the fused GDN MTP kernel has no image, AND silently drop the served window from 1M to 262144. This is the spark-lobe re-render trap that docs/dspark-speculation.md point 8 closed for the Spark, still open in the opposite direction for the Thor
  - instruction: Before any --apply on this box, run the re-render DRY (no --apply) and diff the proposed argv against 'docker inspect'. Never let the speculation spike be the first thing that also silently changes the served window.
- no quality claim rides on this, and an observed divergence triggers INVESTIGATION before any verdict. Block speculation is lossless BY CONSTRUCTION (the target verifies every drafted token) — docs/dspark-speculation.md labels that STRUCTURAL, not measured, and explicitly notes it is 'not a claim that any particular implementation is bug-free: a broken verification path, a mangled config, or a silently-disabled speculative flag can all violate it in practice'. A Triton-vs-CUDA GDN decode swap is a further axis again, touching the non-speculative path too. So this spike measures speed and acceptance only; if an output difference IS observed on a speculative arm, the correct first move is to determine whether it is an implementation defect (config, verification path, parser) or a genuine algorithmic divergence — the structural claim is about the algorithm, and a defect falsifies the deployment, not the algorithm
  - instruction: Run the d1 probe suite (`known_answer`, `tool_calls`, gateway smoke) on EVERY arm, not just the fastest. If outputs differ, record the raw divergence in the transcript before diagnosing it, then check the cheap implementation causes first — argv via docker inspect, sampling parameters, the `qwen3_coder_thinking` parser — before reaching for an algorithmic explanation.
- the DSpark arm executes third-party weights under --trust-remote-code, which the Thor's live cortex argv already carries. RadixArk/Qwen3.8-27B-DSpark is an outside publisher's repo, and a drafter is executable weights — spark-lobe.toml already says so ('an unpinned draft repo is a silent config change on the next pull') and pins the revision. That pin is the whole mitigation, so it must be carried verbatim into the Thor arm and proven from the container's rendered argv, never retyped from memory. Do not run the DSpark arm against a floating main
  - instruction: Copy the `speculative_config` value verbatim from lobes/profiles/`builtin_shapes`/spark-lobe.toml rather than retyping the revision. Mind the double-quoting layers documented there — the bare and unquoted spellings degrade the JSON silently.

## Non-goals

- do not chase the published 34-38 tok/s DGX Spark figure on the Thor. It is PUBLISHED-ELSEWHERE — a different publisher's checkpoint (RadixArk NVFP4), a different engine (SGLang), a different target quantization, on different silicon (`sm_121`, not `sm_110`). docs/dspark-speculation.md already records that this fleet measured its own numbers rather than closing that gap, and a Thor run widens the gap rather than narrowing it
- a single-shape throughput number is not a description of a speculative lane. The Spark spike measured a ~3x content spread (DSpark 46.20 code / 31.73 reasoning / 13.71 prose tok/s at 262144) and recorded ~10-13% single-run variance, so any Thor arm must run at least the same three content shapes, label every number with the shape that produced it, and treat deltas at or under ~15% as noise

## Assumptions

- the Thor's 12.1 tok/s cortex is the NO-SPECULATION floor, not an MTP-assisted rate: docs/evidence/2026-08-20-accept-cortex-local-thor.txt records MTP OFF, and the live 'docker inspect model-gear-vllm-primary' argv today carries no --speculative-config at all. The Spark's own no-spec floor measured 9.93-11.42 tok/s, so 12.1 is the same regime — the prize here is a ~4x speculation multiplier, not the Spark's +64% MTP-to-DSpark delta
- vLLM's own auto-fallback cannot detect this failure: `_fused_gdn_decode_unsupported_reason` (`qwen_gdn_linear_attn.py`:511-533) tests gqa layout, head dims, dtypes, `has_device_capability`(80), and hasattr(torch.ops.`_C`,'`fused_gdn_decode_post_conv_mtp`'). On `sm_110` the symbol IS built and capability IS >= 8.0 — the wheel just ships no `sm_110` SASS image for it — so every guard passes and the failure surfaces at kernel launch. That is why d1 saw a crash on first decode instead of a graceful Triton fallback, and it matches the cuda-wheel-arch lesson (Spark `sm_121` vs Thor `sm_110` are not one arch)
- MTP-n2 and DSpark have IDENTICAL `sm_110` exposure — a hypothesis I formed and then REFUTED by reading the source, recorded so it is not re-argued. I expected the checkpoint's own MTP head to run GDN layers (making MTP the riskier arm on `sm_110`) and DSpark's separate dense drafter to be cleaner. It is not so: `qwen3_5_mtp.py`:118-124 builds the MTP head's decoder layers with `layer_type`='`full_attention`', and `qwen3_dspark.py`'s drafter is likewise full-attention GQA. NEITHER drafter touches GDN. The only `fused_gdn_decode_post_conv_mtp` exposure is the TARGET's verification batch, which `VLLM_GDN_DECODE_KERNEL`=triton covers identically for both. Drafter choice is therefore a pure throughput question on this box, not a kernel-risk question
- the fused-GDN-MTP kernel gap is NOT sidestepped by switching drafter — a SOURCE-READ PREDICTION, never measured, and moot in the shipped design since all three arms run behind the Triton knob regardless. Read in the Thor's OWN running container (vllm 0.26.1rc1.dev942+g5a4c8d992): `qwen_gdn_linear_attn.py`:1798 `_can_use_fused_gdn_mtp_decode` gates on '`spec_sequence_masks` is not None and `num_decodes` == 0 and `num_spec_decodes` > 0' — a property of the TARGET's verification batch, not of which drafter produced it. DSpark's block-7 verification width 8 is <= `MAX_FUSED_GDN_MTP_TOKENS` (8), so on the CUDA path DSpark would launch the same `fused_gdn_decode_post_conv_mtp` kernel that killed the d1 first decode. Recorded so nobody re-proposes 'just use DSpark' as a way around the `sm_110` gap
