- The nightly is a liability: #309 recorded a device-side assert + Xid 43 on 2 of 3 fresh torch.compile runs on the Thor worker under 0.26.1rc1.dev942, and the fleet today runs THREE engines (8bd082c2, 7c5a10e9, 0.31.0) with no engine version in the mesh fingerprint — one pinned official release makes the boxes comparable, debuggable and rebuildable

## Assumptions

- Every other serve flag/env the fleet compose uses exists on v0.31.0 (static grep of the 0.31.0 source): reasoning parsers qwen3/gemma4/`nemotron_v3`, tool parsers `qwen3_coder`/gemma4/lfm2/hermes, --tool-parser-plugin, --default-chat-template-kwargs, --attention-config, --runner=pooling/--convert, --enable-lora/--lora-modules, speculative methods mtp/dspark/dflash, `VLLM_GDN_DECODE_KERNEL`, `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS`, `VLLM_ALLOW_LONG_MAX_MODEL_LEN`, `VLLM_CACHE_ROOT`. Existence is not behaviour: each lane still needs a live boot + probe
- Moving to 0.31.0 does NOT by itself cure the #309 compile crash: docs/plans/2026-10-17-lane-safety-HANDOFF.md:52-53 records the official v0.31.0 Thor worker crashing in inductor Triton autotune (cudaErrorIllegalInstruction, Xid 13 then 43) on warm-cache first boot in 2 of 3 restarts on 2026-10-17, recovered by the Docker restart (upstream vllm#62149); the lane-safety bundle's crash backoff + boot hold remain load-bearing on 0.31.0
- 0.31.0 is a measured improvement for the Thor worker: mjolnir-agent docs/incidents/2026-10-16-thor-safe-boot.md:151-156 records official 0.31.0 Qwen3.6-35B-A3B NVFP4 (fp8 KV, DFlash K=12) decode 80.9/87.0/95.7/80.9 tok/s at depth 0/8K/32K/64K vs nightly production 75.2/82.9/83.7/66.9, KV 330,212-344,212 tokens; Qwen3.8-27B NVFP4 on 0.31.0 served with KV 746,503 (line 91). Those runs were mjolnir's harness, not a lobes render
- Arch coverage is uneven: the official v0.31.0 Dockerfile's `torch_cuda_arch_list` is '7.5 8.0 8.6 8.9 9.0 10.0 11.0 12.0' — `sm_110` (Thor) listed, `sm_121` (GB10) only via 12.0 same-major compat, `sm_87` (Orin) NOT listed — yet docs/evidence/2026-10-14-ab-clef-vllm-vs-sidecar-orin.txt:10-18 MEASURED vllm 0.31.0 serving W4A16 via Marlin + `FLASH_ATTN` on the Orin's `sm_87`. Measured evidence wins, but it covers one pooling workload only; every other lane on each arch needs its own boot
- The mesh fingerprint does NOT include the engine version: Fingerprint is `served_id`, quantization, `max_model_len`, runtime (lobes/gateway/`_mesh_wire.py`:86-89, mirrored in `_replicas.py`:298). So during the per-box rollout a 0.31.0 Spark cortex and a nightly spark2 cortex agree and pool as one plain 'cortex' — invisible mixed engines; every baseline and re-measure must address the member lanes cortex-spark / cortex-spark2 (or the lane directly), never plain cortex
- The lane-safety safety net that c14 leans on is NOT on any box: the 0.88.0 template mounts /cache/vllm in 36 places, while the deployed docker-compose.yml on spark, spark2, thor and orin has 0 (they run `MODEL_GEAR_VERSION` 0.86.0.dev6xx). A new engine changes vLLM's compile `config_hash`, so EVERY lane's first boot on 0.31.0 is a cold compile — the boot class where #309 crashed — with no crash backoff, boot hold or per-lane cache on the box
- The Spark is the mesh's only innereye (ComfyUI) host — `INNEREYE_FEASIBLE` appears only in the Spark's .env (:773), not on spark2, thor or orin — so 'either cortex or innereye' (decision c35) means innereye is unavailable mesh-wide whenever the Spark serves cortex, and its callers get `role_infeasible` for that window
- spark2 is the same DGX Spark GB10 hardware as the Spark, and the incumbent baselines plus 0.31.0 re-measures are sustained full-GPU benchmark runs — the load class that hard-resets a Spark thermally (memory record spark-thermal-resets-governor, #304) — yet the governor decision (c30) names only the Spark's lane
- The ubuntu2404 variant is proven on ONE architecture only: the Thor worker (`sm_110`) serves on v0.31.0-ubuntu2404; every Orin (`sm_87`) 0.31.0 measurement — the decider's 0.988 top-1 agreement and the orin-decider acceptance (docs/evidence/2026-10-14-\*) — ran on PLAIN v0.31.0 (index c1c9f6fd, arm64 3f7dd5b7), and no GB10 0.31.0 lobes lane has run yet. Moving Dockerfile.decider-vllm to -ubuntu2404 (c40) turns the decider's MEASURED values into DECLARED until re-measured
- 0.31.0 adds `VLLM_ENFORCE_STRICT_TOOL_CALLING` (envs.py:245, default True), which gates the structural-tag path that strict tool schemas use — so strict-tool behaviour can change on lanes beyond cortex (worker, hand, and the gateway's `GATEWAY_FORCE_STRICT_TOOLS` opt-in), not only through the plugin's signature

## Decisions

- The fleet pin is vllm/vllm-openai:v0.31.0-ubuntu2404 (index sha256:3fb023cc987cc7c2bca7ca14c1e0aff5ae06bd9431bf07773731ce7e8a682460), the variant the Thor worker already serves
- Rollout is per-box override first: baseline the incumbent, apply `VLLM_NIGHTLY_IMAGE` as a .env override on one box, validate, then the next box; the template default flips and a release ships only after the boxes validate
- In scope beyond the shared pin: the torch-only bases Dockerfile.embed-st (`ST_BASE_IMAGE`, carries the Orin's live gemma2-embed sidecar) and Dockerfile.decider (`DECIDER_BASE_IMAGE`). Out: Dockerfile.vllm-gemma4, vllm-minor/middle + the legacy single compose (NGC 26.04-py3), and the Orin `ASSOCIATE_IMAGE` (stays v0.27.1)
- The Spark lane gets adaptive CPU cores per temperature, as jev-factory did, which stopped the Spark's thermal resets
  - instruction: Applies to the Spark's cortex lane (vllm-primary) on 0.31.0 — the decision outlives the Super VL rejection
- On the Spark it is either cortex or innereye (ComfyUI), never both at once: bringing cortex up stops ComfyUI, and bringing ComfyUI back stops cortex
- Lane-safety is a precondition: each box moves to the 0.88 scaffold (crash backoff, boot hold, per-lane compile cache, refreshed logwrap and plugin copies) BEFORE its engine switches to 0.31.0
- spark2's nightly cortex baseline is the Spark's comparator (same checkpoint and silicon), cross-referenced with the Spark's 2026-10-06 measurement; the Spark does not boot cortex on the nightly first
- spark2's baseline and re-measure benchmark runs also run under the thermal governor
- The decider-vllm sidecar moves to v0.31.0-ubuntu2404 for the strict one-pin rule; its 0.988 agreement and orin-decider acceptance values become DECLARED until re-measured on the Orin
