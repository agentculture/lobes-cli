# lane safety and quality (#304 #307 #308 #309)

> lobes lanes boot, compile and run safely: GPU services hold after a power cycle, the vLLM compile cache survives a recreate, a hot box sheds load instead of power-cycling, and clocks stay stock outside an explicit benchmark window

## Audience

- Operators of lobes boxes (DGX Spark, Jetson AGX Thor, Jetson AGX Orin) and the agents that run lobes verbs on them in loops; secondarily mesh callers who receive a 429 from a hot box

## Before → After

- Before: Today: a power-cycled box restarts every lane within ~8 s of dockerd, before ssh is possible; every compose recreate recompiles torch.compile from scratch in the writable layer (2 of 3 fresh Thor compiles hit a device-side assert + Xid 43); a crashed lane restarts immediately into memory the crash still holds; the Spark power-cycled twice under sustained full-GPU load with no lobes thermal awareness; benchmark numbers carry no recorded power mode, clocks or temperatures
- After: After a power cycle every lobes service waits until host uptime >= 120 s; a recreate reuses the lane's compile cache; a repeatedly crashing lane backs off instead of looping into held memory; a box over its per-card thermal threshold sheds sheddable tiers with 429 instead of heating further; lobes benchmark runs inside a locked-clocks window delegated to the machine CLI and always restores stock DVFS, recording conditions in the result

## Why it matters

- A hung box that brings its own crash straight back cannot be rescued remotely, and a box that power-cycles under load loses in-flight work and evidence; unrecorded clocks make benchmark numbers irreproducible (docs/measuring-lane-performance.md Rule 2 already cost one wrong conclusion)

- Healthcheck `start_period` is raised to cover the boot hold on every wrapped lane (vLLM lanes are 600s today) so a held container is not marked unhealthy, or the hold is shown to fit inside the existing `start_period`

## Scope / boundaries

- Thor carries experimental work: this effort may change code, templates, tests, docs and goldens, but must NOT deploy, recreate or restart anything on the Thor; live Thor validation is deferred and stays DECLARED/UNVALIDATED (#108)
- restart: unless-stopped stays on every service (it is the only policy in every template today, no on-failure anywhere); the boot hold is what makes auto-restart safe, not a policy change
- lobes never clears caches from inside a container and never uses full sudo: the clear runs host-side only, through a single NOPASSWD sudoers rule for '/usr/sbin/sysctl -w vm.`drop_caches`=3' (mjolnir cachectl pattern), and never prompts — no grant means skip and say so
- Serving lanes are NEVER paused and NEVER docker update'd by any lobes governor: pause freezes in-flight requests, and docker update --cpus is a correlated (unproven) suspect for cudaErrorNotPermitted on GPU containers (#304 comments 2 and 3)
- No persistent clock or fan change from lobes init, serve, switch or any deployment; production stays stock DVFS + the host's nvfancontrol profile

## Non-goals

- No batch-job governor ships in this effort: the ~/odm/telemetry pause governor (hardcoded container odm-clef-quant-w4a16, no lobes awareness) stays an operator script; batch training/quant moved to jev-factory (lobes only hosts)

## Assumptions

- Editing mg-logwrap.sh changes its sha256 recorded in deployments/\*/deployment.lock.toml and the verbatim deployments/\*/mg-logwrap.sh copies; the repo-side catalog copies are NOT regenerated from a live box (Thor no-deploy) — `lock_drift` on a live box is the expected signal until each box re-scaffolds
- Mounting the cache only masks the #309 device-side assert (index out of bounds 0 <= tmp13 < 1048576 in `profile_run` on nightly 0.26.1rc1.dev942); root-causing it or moving the Thor worker off the nightly is separate work and needs Thor time, so it is out of this code-only effort
- On a reboot dockerd restarts containers by restart policy alone and does NOT honour compose `depends_on`, so a boot hold must live in each container's own entrypoint; a single compose-level 'hold' service that others depend on would be skipped exactly when it matters
- Thermal shedding only refuses NEW gateway requests: it does not cool a box running a long in-flight request (a 1M prefill runs ~40 min) or a non-lobes workload, and the two Spark resets in #304 happened under a non-lobes batch quant container — so the shed signal protects serving load, and does not by itself prevent the incident #304 recorded

## Decisions

- Benchmark windows LOCK clocks/fan (not just record) as the general standard; machine work lives in the per-machine CLIs — dgx-spark-cli (spark), jetson-thor-cli (thor), jetson-orin-cli (orin) — which lobes depends on and delegates to; PRs on those repos are in scope (operator, 2026-10-17)
- Boot hold: `LOBES_BOOT_DELAY_S` default 120 before every service lobes starts, every card (operator, 2026-10-17)
- Delivery: one bundle PR; quick pieces split out as stacked PRs to keep the bigger PRs focused (operator, 2026-10-17)
- Machine CLIs are OPTIONAL runtime dependencies of lobes (extras or PATH lookup), not hard pyproject dependencies: a gateway image or an unknown card must not pull three device CLIs
- Crash backoff = Option C: wrapper start-rate counter as backstop + pre-exec memory gate on the lane's gpu-memory-utilization share; restart: unless-stopped kept (operator, 2026-10-17)
- Add a page-cache clear (vm.`drop_caches`=3) the way thor-arena/mjolnir does it — proven in mjolnir-agent's Thor incidents (operator, 2026-10-17)
- The cache clear and its grant live in the machine CLIs (spark / thor / orin drop-caches + grant-permissions), consistent with c25 'machine work lives there'; lobes calls them, falling back to sudo -n sysctl when the rule exists but no machine CLI is installed
- Gated-lane cache clear: gate timeout + operator message (b) AND a lobes-owned host watcher (a) that clears the cache when a lane is gated; lobes owns it because it is a lobes-specific need (operator, 2026-10-17)

## Hard questions

- On Thor, crash-freed memory stays out of MemAvailable until `drop_caches` (mjolnir-agent incident Q7), and a container cannot clear caches: after a dockerd-driven restart (no lobes verb involved) the gate would wait forever. What clears the cache on that path — a host systemd unit/path watcher shipped via the machine CLI, a gate timeout that tells the operator to run the clear, or accept the hold as the safe outcome? (resolved: Both: (b) the memory gate times out with a logged reason telling the operator how to clear; AND (a) a host-side watcher that clears the cache when a lane is gated — owned by lobes, not the machine CLIs, because it is a lobes-specific need (operator, 2026-10-17))
